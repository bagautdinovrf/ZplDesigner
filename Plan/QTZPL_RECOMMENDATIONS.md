# Рекомендации по развитию QtZpl для новой архитектуры Designer

Дата: 9 октября 2026 года. Статус: предложения по текущим исходникам; расширения API не реализованы в рамках подготовки документа.

Основной документ: [проект реорганизации Designer](REFACTORING_PLAN.md).
Рекомендации предназначены для отдельных задач в соседнем `../qt-zpl`. Здесь хранится описание потребностей потребителя; исходники библиотеки этим документом не изменяются.

Пути в примерах и команды указаны относительно корня соответствующего репозитория.

## 1. Основной вывод

Реорганизацию Designer можно начать с существующим API QtZpl. Выделение операций, состояний исходника, панелей и координатора превью не требует предварительной переработки библиотеки.

Развитие QtZpl полезно там, где Designer вынужден повторно разбирать ZPL, самостоятельно воспроизводить действующие настройки принтера, рендерить каждый объект ради его границ или восстанавливать связь диагностики с исходником. Расширения должны убрать конкретные обходные решения, сохранив самостоятельность библиотеки.

Приоритетный небольшой пакет: согласовать контракт данных поля, добавить рендер выбранной этикетки из `Document`, определить точные диапазоны исходника. Анализ полей и геометрия — следующий, более крупный пакет. Фоновый рендер и отмена не являются предварительным условием новой архитектуры.

## 2. Что уже есть и должно быть использовано

Проверены публичные `include/QtZpl/qtzpl.hpp`, `include/QtZpl/model.hpp`, реализации parser/renderer и адаптеры Designer. Это статический просмотр; текущие сборки, тесты и измерения производительности не выполнялись.

| Возможность | Текущее состояние | Вывод для планирования |
|---|---|---|
| Отдельный разбор | `parse(QStringView, ParseOptions)` возвращает `Document` | Не нужен новый парсер внутри Designer |
| Рендер разобранного документа | Уже есть `render(const Document&, RenderOptions)` | Переиспользование результата parse уже возможно |
| Модель для чтения | `Document`/`Label` не предоставляют потребителю изменяемую модель | Сохранить эту границу; редактор владеет своей моделью |
| Типизированные команды | `CommandPayload` описывает команды | Использовать вместо строковых догадок, где хватает публичного контракта |
| Диагностика | Уже есть severity, code, message, offset, command | Сначала не терять эти данные в адаптере Designer |
| Неизвестные команды | Есть `UnknownCommand` и `preserveUnknownCommands` | Сохранить отказоустойчивую обработку |
| Позиции команд | Есть `Command.offset` и `Command.source` | Уточнить точность: `source` не гарантирует дословный raw token |
| Несколько этикеток | Полный render возвращает список изображений | Нужен дополнительный выбор одной этикетки без рендера всех |
| Ограничения ресурсов | В реализации есть проверки размеров и других опасных значений | Предложение касается публичного бюджета и единых правил, а не отсутствия защиты |
| Параллельный рендер | Правила проекта требуют его; есть контекст шрифтов на вызов и concurrency tests | Документировать и проверять расширения того же контракта |

Опорные места в библиотеке: `include/QtZpl/qtzpl.hpp`, `include/QtZpl/model.hpp`, `src/parser.cpp`, `src/renderer.cpp`, `tests/test_qtzpl.cpp`, `tests/test_renderer_performance.cpp`.

Опорные места в Designer: [preview_renderer.cpp](../src/core/preview_renderer.cpp), [zpl_codec.cpp](../src/core/zpl_codec.cpp), [zpl_source_map.cpp](../src/core/zpl_source_map.cpp), [document_validation.cpp](../src/core/document_validation.cpp), [design_internal.hpp](../src/core/design_internal.hpp).

## 3. Граница ответственности

**QtZpl владеет:** синтаксисом и семантикой ZPL, порядком команд и этикеток, кодировками полей, действующим состоянием принтера при интерпретации, декодированием ZPL-графики, рендером и его диагностикой.

**Designer владеет:** изменяемым документом, UUID объектов, группами и таблицами как редакторскими сущностями, визуальными операциями, undo, выделением, черновиком текста, `.qtzpl`, плейсхолдерами приложения, генерацией ZPL и преобразованием импортированных картинок. Он же решает, какое подмножество команд можно безопасно редактировать визуально.

Печать, транспорт, autosave и интерфейс не переносятся в QtZpl. Разобранная модель библиотеки не становится изменяемым документом редактора. Наличие геометрии или распознанного поля само по себе не доказывает возможность визуального редактирования без потерь.

## 4. Предлагаемые расширения

Ниже P0 означает приоритет корректности данных, P1 — сокращение сложности адаптера, P2 — улучшение по подтверждённой потребности. Приоритет не означает, что все работы блокируют реорганизацию Designer.

### QZ-01 · P0 · Явный контракт Unicode и байтов поля

**Наблюдение.** `FieldData` содержит `QString data`. Парсер при `^CI28/^FH` декодирует UTF-8 в Unicode. В рендерере для ряда штрихкодов есть проверки и преобразования, ожидающие байтовое представление, в частности DataMatrix. Это место требует единого контракта между parser и encoder. Историческое падение Designer `dataMatrixUtf8BytesRoundTrip` описано в README, но его текущий статус нужно подтвердить новым прогоном перед исправлением.

**Предложение.** Явно определить и при необходимости представить раздельно:

- исходное написание payload;
- декодированный текст;
- байты, полученные по правилам кодировки поля и `^FH`;
- активную кодировку и семантику управляющих маркеров.

Точный состав публичной структуры согласовать по реальным потребителям. Не менять молча смысл существующего `FieldData::data` и не получать байты через неявный `toLatin1()`. Для каждого семейства штрихкодов определить допустимую кодировку и поведение неподдерживаемых данных. FNC1, ASCII GS и текстовое обозначение разделителя различаются.

**Приёмка.** Проверки parser → encoder для ASCII, кириллицы при UTF-8, смешанного прямого текста и hex escapes, GS, NUL и применимых бинарных значений. Некорректные последовательности дают документированный результат/диагностику. Нет двойного UTF-8-кодирования; уже принятые ASCII/GS1-векторы не меняются. Где данные недопустимы для выбранной символики, ожидается конкретный отказ, а не обязательный успешный рендер.

**Для Designer.** Нужен для корректной поддержки соответствующих данных. Выделение UI и сессии может идти независимо. Редактор не должен компенсировать расхождение сменой кодировки «до похожей картинки».

### QZ-02 · P1 · Рендер выбранной этикетки из Document

**Наблюдение.** `render(const Document&)` уже существует, но работает со всем документом. `checkedRenderPage()` в Designer разбирает поток, вырезает исходник страницы, повторно вызывает строковый render и сдвигает offsets диагностик.

**Предложение.** Добавить совместимое расширение наподобие `renderLabel(document, labelIndex, options)`. Имя иллюстративное. Оно возвращает изображение выбранной этикетки и диагностику с исходными индексами/позициями. Семантика состояния, ресурсов и команд предыдущих этикеток должна совпадать с полным рендером; выбор страницы не означает произвольный запуск от вырезанной строки.

**Приёмка.** Для каждой страницы растр совпадает с соответствующим результатом полного render при тех же options. Проверены наследование состояния, неверный индекс, многостраничный источник, ошибки на выбранной странице и политика общих parse-диагностик. Невыбранные страницы не требуют выделения полноразмерных растров. Единицы offsets остаются прежними.

**Для Designer.** Удаляет вырезание `labelSource()` и ручную поправку offsets. Не является обязательным условием R1–R4 основного плана.

### QZ-03 · P1 · Точные диапазоны и сохранение исходного текста

**Наблюдение.** `Command.offset` уже есть. Но парсер реконструирует `Command.source`: например, нормализует opcode, а чтение некоторых параметров удаляет переводы строк. Поэтому длина `source` не во всех случаях определяет точный конец исходной команды.

**Предложение.** Сохранить оригинальный ввод в неизменяемом документе либо ином объекте с явным временем жизни и дать точные `SourceSpan {start, length}` для команд, этикеток и полей. Нормализованное представление можно оставить отдельно. Прямо описать текст вне `^XA…^XZ`, разделители, комментарии, неизвестные команды, пустые параметры и команды изменения разделителей.

Для существующего `QStringView` API смещения определять в UTF-16 единицах исходной QString. Это не обещание побайтной реконструкции произвольной входной кодировки файла. Если потребуется byte-oriented API, его контракт и отображение позиций задаются отдельно.

**Приёмка.** Подстрока по каждому span точно совпадает с исходным фрагментом для lowercase-команд, пробелов, CRLF, кириллицы, суррогатных пар, unknown commands, hex data и соседних этикеток. Проверены границы диапазонов и владение строкой после завершения `parse`. Неподдерживаемый текст не исчезает из сохранённого источника.

**Для Designer.** Позволяет упростить карту исходника и lossless-импорт. До выполнения этого контракта собственные исходные токены и защитные проверки редактора сохраняются.

### QZ-04 · P1 · Анализ полей и действующих настроек

**Наблюдение.** `fromZpl()` в Designer самостоятельно ведёт состояние шрифтов, `^BY`, `^CI`, origin, ориентации и времени действия команд. Рендерер также имеет собственный `State`. Карта исходника ещё раз разбирает границы полей.

**Предложение.** Добавить API только для чтения, представляющий семантические поля: диапазоны исходника, принадлежность этикетке, тип, эффективные настройки и диагностику. Он должен опираться на ту же реализацию применения команд, что и renderer, чтобы не создавать третью версию интерпретатора.

ID поля относится к конкретному разобранному снимку. Его стабильность между разными вызовами parse не обещается. Один объект Designer, например таблица, может соответствовать нескольким полям QtZpl; это отображение хранит редактор.

**Приёмка.** Анализ и render одинаково трактуют `^FO/^FT`, `^FW`, шрифты, `^BY`, `^CI`, `^FH`, `^LH`, трансформации и завершение поля. Неизвестные команды отмечены явно. Неоднозначность не превращается в уверенное разрешение на визуальный импорт. Выполнение анализа не требует растеризации каждой этикетки.

**Для Designer.** Уменьшает дублирование семантики. Вводить после уточнения QZ-01/QZ-03, отдельными группами команд. Собственная модель и решение `visualEditable` остаются в Designer.

### QZ-05 · P1 · Геометрия полей из того же прохода рендера

**Наблюдение.** `RenderResult` сейчас содержит изображения и диагностику. В Designer часть bounds вычисляется вручную, а для текста, изображений и кодов создаётся отдельный документ, строится его растр и сканируются чёрные пиксели. Для ошибочных кодов есть дополнительные проверки через рендер.

**Предложение.** Опционально выдавать вместе с результатом геометрию и статус каждого поля, связанные с ID/span этого же снимка. Согласовать различные понятия:

| Данные | Назначение |
|---|---|
| Логическая геометрия | Размер и привязка поля до отсечения |
| Область фактического рисования | Собственный рисунок поля и подписи, с оговорённой семантикой |
| Область после clipping | Часть поля в пределах выводимой этикетки |
| Anchor/baseline и трансформация | Сопоставление координат ZPL, растра и маркеров редактора |
| Статус поля | Нарисовано, пусто, полностью обрезано, неподдерживаемо либо ошибка |

Для белых фигур, reverse и перекрытий чёрные пиксели итоговой страницы не определяют геометрию отдельного поля. Точность и систему координат каждого вида bounds нужно описать, включая выход подписи за якорь и поворот этикетки. Отсутствие рисунка не означает отсутствие редактируемого объекта.

**Приёмка.** Поля геометрии и растр получены из согласованного состояния. Проверены текст с выносными элементами, `^FT`, `^FB`, подписи штрихкодов, все ориентации, `^PO/^PM`, белые/reverse-поля, перекрытия и clipping. Режим без метаданных сохраняет прежний результат и не получает необоснованных дополнительных затрат.

**Для Designer.** Убирает повторные полные рендеры ради hit testing и resize. Сначала включить метаданные параллельно с имеющимися проверками, затем удалить только заменённые обходные вычисления. Редакторский fallback для ошибочных полей остаётся отдельной политикой.

### QZ-06 · P1 · Сохранить и уточнить структурированную диагностику

**Наблюдение.** В QtZpl диагностика уже структурирована. Designer местами преобразует её в `QStringList` и сохраняет только текст с offset, теряя код, важность и связь с полем.

**Первый шаг — в Designer.** Сохранять структуру до уровня представления. Локализованный текст формировать при показе, не анализировать текст сообщения для принятия решений.

**Расширение QtZpl.** При необходимости добавить необязательные label index, field ID и source span. Зафиксировать стабильность машинных codes и политику объединения parse/render diagnostics, особенно при рендере одной страницы из уже разобранного документа.

**Приёмка.** Ошибка данных штрихкода ведёт к нужному полю нужной страницы; повторное использование `Document` не размножает сообщения; ошибки без точного диапазона остаются общими, а не получают выдуманный offset. Новые поля не ломают существующие сценарии потребителей.

### QZ-07 · P2 · Декодирование импортированной графики

**Наблюдение.** Для восстановления `^GF` в `zpl_codec.cpp` Designer строит искусственную этикетку и рендерит её. Алгоритмы распаковки уже есть в QtZpl.

**Предложение.** При достаточной пользе дать небольшой read-only декодер графического поля с размерами, packed data либо монохромным изображением и диагностикой. Публичный контракт должен переиспользовать существующие алгоритмы, проверять размеры и лимиты распаковки. Не открывать внутренний helper без проверки его пригодности для внешнего API.

**Приёмка.** ASCII/compressed/Z64-входы, неполная последняя строка, некорректные данные и граничные размеры. Результат совпадает с графикой штатного renderer; ошибки не приводят к неограниченной распаковке.

**Для Designer.** Упрощает импорт. Преобразование нового PNG в ZPL и выбор dithering/threshold остаются в редакторе.

### QZ-08 · P1/P2 · Ресурсный бюджет и конкурентное выполнение

**Наблюдение.** У библиотеки есть внутренние ограничения и тесты конкурентного render, но публичные options не дают единого настраиваемого бюджета. Часть дополнительных проверок выполняется в Designer уже после parse.

**P1 — договориться о лимитах.** Рассмотреть ограничения длины источника, количества команд/этикеток, суммарных пикселей, распакованных данных и объёма диагностик. Сохранить безопасные значения по умолчанию и проверки до опасных выделений памяти. Продуктовые ограничения Designer, например число редактируемых объектов, остаются в приложении.

**P1 — описать существующую конкурентную модель.** Зафиксировать требования к Qt application, времени жизни входного `Document`, независимости результатов и работе шрифтов/ресурсов при первом вызове. Новые page/analysis/geometry API включать в проверки одновременного первого и повторного запуска. Результат может быть обычным изменяемым значением у владельца; существенно отсутствие общей несинхронизированной изменяемой памяти.

**P2 — отмена и кэширование.** Добавлять после измерений дорогих сценариев. Если нужна отмена, определить границы проверки stop request и результат отменённой операции. Кэш ограничивать по памяти и ключам; не вводить глобальный неограниченный кэш как часть выделения API.

**Приёмка.** Превышение бюджета даёт стабильную ошибку до опасной аллокации; обычные fixtures сохраняют результат. Независимые потоки получают одинаковые изображения и диагностику. Отмена, если добавлена, не публикует неполное изображение как успешный результат.

## 5. Организация кода QtZpl

Сохранить компактный публичный API и текущие обязанности библиотеки. Для удобства работы с ИИ полезно разделять внутренние компоненты по тому, что они проверяют:

| Компонент | Контракт | Подходящая проверка |
|---|---|---|
| Чтение исходника | Точные диапазоны, разделители, пустые параметры, восстановление после ошибки | Маленькие синтетические входы и fuzz/property checks |
| Интерпретация полей | Состояние команд, кодировки, привязки и lifetime | Сравнение ожидаемых effective settings и payload |
| Геометрия и композиция | Преобразования, clipping, порядок, reverse | Геометрические проверки и принятые Labelary goldens |
| Кодировщики | Данные → модули конкретной символики | Известные векторы независимо от QPainter |
| Шрифты и ресурсы | Детерминированность и независимость контекста | Векторы/изображения, первый конкурентный вызов |
| Публичный фасад | Ошибки, options, lifetime, совместимость | Небольшие consumer-тесты через публичные headers |

Новые внутренние файлы вводить при выделении конкретной обязанности. Действующий AGENTS.md QtZpl задаёт `src/parser.cpp` и `src/renderer.cpp` как места реализации; при принятом изменении организации одновременно обновить эту карту, сохранив публичные точки входа. Не делать массовое разбиение перед функциональными контрактами.

Полезно держать в репозитории библиотеки короткий документ с гарантиями API: кодировка/единицы offsets, системы координат, страницы, диагностики, ресурсы, потоки и статус поддержки команд. Рядом с каждым расширением — минимальный пример потребителя и список проверок. Поддержка команды парсером, корректный рендер и возможность её визуального редактирования в Designer — три разных свойства.

## 6. Совместимость API и порядок двух репозиториев

Ниже указана последовательность будущей работы, а не требование выполнить её целиком до реорганизации Designer.

1. В Designer выделить адаптер библиотеки и сохранить структурированные diagnostics. Связать parsed snapshot с точным source text/options и его ревизией. Генерируемый ZPL и заполненный плейсхолдерами ZPL — разные входы и не должны делить неподходящий кэш.
2. В QtZpl зафиксировать контракт QZ-01 и свежие регрессионные случаи. Устранение ошибки кодировки оформить отдельно от крупного архитектурного переноса.
3. Добавить QZ-02 и QZ-03 как небольшие расширения с consumer-тестами. Сохранить текущие overloads и defaults.
4. Переключить соответствующие части адаптера Designer, проверив прежнее поведение. Удалить заменённые обходные решения.
5. Реализовать QZ-04/QZ-05 по согласованному контракту семантики и геометрии. Расширять диагностику вместе с появлением field identity.
6. QZ-07, бюджеты, отмену и оптимизации выполнять по подтверждённой потребности; публичные гарантии конкурентного выполнения уточнить до запуска новых API в фоне.

Совместимость исходников и двоичная совместимость — отдельные вопросы. Добавление полей в экспортируемые структуры может менять ABI даже при сохранении исходных вызовов. Для каждого изменения записывать влияние на shared/static потребителей и порядок пересборки/версионирования; не называть расширение автоматически ABI-совместимым.

Во время перехода Designer продолжает собираться с текущим соседним checkout. Не использовать старую копию QtZpl ради зелёной проверки. Если изменения выполняются параллельно, фиксировать проверенные ревизии и незавершённые контракты. Чужие локальные изменения не откатывать.

## 7. Набор проверок на границе библиотек

Создать небольшой синтетический consumer corpus, используемый для проверки публичного API QtZpl и его адаптера в Designer. Эталонные ожидания должны иметь понятного владельца; не заводить две расходящиеся копии ожидаемой семантики.

| Сценарий | Что фиксируем |
|---|---|
| Несколько этикеток | Порядок, выбранная страница, состояние и offsets относительно полного источника |
| Unicode и `^FH` | Текст/байты/кодировка, отсутствие двойного преобразования, ошибки |
| Неизвестные команды | Точный source span, сохранённый текст, стабильная диагностика |
| Пустые параметры и CRLF | Позиции параметров и дословные диапазоны |
| `^FO/^FT`, `^FW`, `^BY`, `^LH` | Согласованная семантика анализа и renderer |
| Текст и подписи штрихкодов | Логическая геометрия, область рисунка, clipping и повороты |
| Белые/reverse/перекрывающиеся поля | Явная геометрия без эвристики итоговых чёрных пикселей |
| Ошибочный код | Диагностика поля, отсутствие ложного символа, возможность редакторского fallback |
| ASCII/compressed/Z64-графика | Распаковка, размеры, resource budget и ошибки |
| Конкурентные вызовы | Первый запуск, общий read-only Document, независимые результаты |

Сначала завершить связанный пакет изменений, затем проводить проверки. Стандартная финальная команда обеих кодовых баз:

```text
py -3 tools/build_helper.py all --clean --config Debug
```

Запускать её отдельно из соответствующего репозитория и следовать его текущему AGENTS.md относительно каталогов сборки и журналов. Для QtZpl дополнительно сохранить проверку shared/static; для изменений производительности выполнить Release-проверку с сопоставимыми входами. Не изменять Qt Creator build trees.

Растровые эталоны — принятые bitonal-изображения Labelary. Обычные тесты работают локально. Корпус go-zpl допустим как источник ZPL-входов, но его растр не используется для приёмки. Известные отклонения, например в шрифтах, фиксировать по свежему прогону и не скрывать изменением допусков при реорганизации.

Этап 1 адаптации Designer (2026-10-22): все вызовы QtZpl идут через
`src/core/qtzpl_adapter.cpp` с бюджетами и общим кэшем разборов; концы команд
берутся из `Command::sourceSpan`; `^GF` импортируется через `decodeGraphic`,
предел Z64 в 16 КиБ снят; превью одной ревизии строятся из одной сериализации,
рамки и ошибки штрихкодов привязываются к полям по `payloadSpan`/`fieldId`;
импорт читает шрифт, `^BY`, `^FB`, `^FP` и `^CI` из `analyzeLabel`; превью
строится в фоновом потоке с отменой. Оставлено: оценки промежуточных растров
в `validateParsed` (у QtZpl нет бюджета промежуточных растров) и отслеживание
`^FW` на момент `^FO` в импорте.

Одному агенту назначать владение публичными headers и интеграцией. Другие могут готовить независимые тестовые векторы, реализацию выбранного encoder или адаптер потребителя после фиксации контракта. Конкурирующие изменения общей структуры `State`, parser и модели полей сначала согласуются, затем разделяются.

Для каждой задачи достаточно указать: какую текущую сложность она устраняет, публичный контракт, сохраняемое поведение, проверки и конкретный обход в Designer, который станет ненужным. Выполненный пакет отмечается после проверки обеих сторон, если адаптер уже на него переведён.
